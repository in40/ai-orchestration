# OpenSpec в нашей команде: исследование применимости

Дата: 2026-11-26. Источник: github.com/Fission-AI/OpenSpec (v2.x, MIT, ~75k звёзд,
CLI `@fission-ai/openspec`, Node ≥22), docs openspec.dev.

## Что такое OpenSpec

Spec-driven development слой для AI-кодеров: до кода человек и агент
договариваются о «что строим» в виде markdown-артефактов в репозитории:

```
openspec/
  changes/<имя-изменения>/
    proposal.md   # зачем и что меняется
    specs/        # требования и сценарии (дельты к текущим)
    design.md     # технический подход
    tasks.md      # чек-лист реализации
  changes/archive/YYYY-MM-DD-<имя>/   # после завершения
  specs/          # живая спецификация текущего состояния системы
```

Жизненный цикл: `explore` → `propose` → `apply` (реализация по tasks.md) →
`archive` (дельты вливаются в живые specs). Всё — согласованный markdown;
CLI в основном генерирует папки/скиллы и валидирует формат. 30+ интеграций с
AI-инструментами через skills. «Stores» (beta) — вынос openspec/ в отдельный
репозиторий для кросс-репо планирования.

## Что у нас уже есть (карта соответствий)

| OpenSpec | У нас | Пробел |
|---|---|---|
| proposal.md (зачем/что) | описание задачи в дашборде | не структурировано, не утверждается человеком |
| specs/ + сценарии | requirements-engineer (декомпозиция), acceptance_criteria в метаданных | существует, но не артефакт: не хранится, не версионируется, гейты по нему не проверяют |
| design.md | MANIFEST.md + план планировщика | генерируется машиной для машины, человек не видит/не утверждает |
| tasks.md | file_manifest (путь+spec на файл) | ~1:1, готовый конвертер |
| apply | coder (opencode-сессия) | есть |
| archive + живые specs | documentation-engineer (post-hoc REQUIREMENTS/ARCHITECTURE/USAGE в results-репо) | **главный разрыв**: документы генерируются ПОСЛЕ и из кода, а спецификация ДО согласования с человеком не существует |
| store (план-репо) | product-зеркала на .187 | у продуктов нет openspec-слоя; зеркала содержат только код |
| clarify с человеком | колокольчик clarifications | есть, но про «значения», не про «утверди план» |

## Главный аргумент «за» — наш собственный провал

Angular→React репетиция №1 (task-1795541246696): кодер получил текстовый бриф
без исходника и без утверждённой спецификации — и **сочинил другой сайт**
(«Софт Тойз» вместо «ПлюшХобби»), гейты пропустили. Репетиция №2 прошла
через product-привязку — порт удался. OpenSpec формализует ровно то, чего не
хватало в №1: утверждённый до кода документ «что является истиной» +
сценарии приёмки, по которым QA может сверять. Это его прямое назначение
(«AI unpredictable when requirements live only in chat history»).

## Варианты внедрения

**A. Формат без инструментов (рекомендую).** Взять только структуру
артефактов, ничего не устанавливать (у нас python-стек, Node-CLI не нужен):
0. **местохранение change-папки зависит от типа задачи, а не наоборот:**
   - зелёнополяная задача (большинство): `results/<task>/openspec/` —
     укороченный цикл propose → approve → apply → done; живой спеки и archive
     нет, change-папка задачи = запись «что согласовали»;
   - продуктовая задача (редко, ценно): change в product-зеркало, полный
     цикл с archive и живыми `openspec/specs/` продукта — накопление
     спецификации нужно только там, где итерации повторяются;
   - задачи к самой платформе (self-fix/оркестрация): `openspec/`
     оркестрационного репо (позже, P3).
   Approval-гейт и приёмка по сценариям **едины для всех случаев**.
1. requirements-engineer вместо свободной декомпозиции пишет
   `openspec/changes/<task>/` (proposal + specs-дельты со сценариями +
   design + tasks) в местохранение из п.0;
2. IT Lead показывает это человеку через колокольчик как **approval gate**
   (полный текст change'а в теле вопроса clarifications — отдельный UI для
   обзора не нужен) — статус awaiting_input уже есть;
3. coder получает tasks.md как MANIFEST (конвертер 1:1);
4. QA-гейт проверяет сценарии из specs (контракт-планер уже строит smoke по
   артефакту — добавляется источник «сценарии спецификации»);
5. только продукты: docs-шаг на done архивирует change (дельты → живые
   `specs/` в зеркале). documentation-engineer получает новый вход:
   согласованные specs вместо гадания по коду.

**B. Полный CLI+skills.** openspec init в оркестрационном репо, coder ходит
через /openspec-* скиллы. Противоречит нашей оркестрации (у нас workflow —
это пайплайн, не чат-сессия), добавляет Node-зависимость ради генерации
папок. Не рекомендуется.

**C. Не внедрять.** Наш набор частично покрывает: MANIFEST≈tasks, docs≈specs.
Но именно «до-кодовое согласование + живая спецификация продукта» не покрыто
ничем — это и есть причина свежих инцидентов. Теряем дешёвый выигрыш.

## Риск/цена варианта A

- задержка на approval gate — решается флагом задачи `spec_first: true|false`
  (по умолчанию false для мелких правок, true для продуктовых итераций);
- пересечение docs-engineer и specs/ — развести явно: specs = «что должно
  быть» (до кода, истина), docs = «как сделано» (после кода, объяснение);
- объём работ: промпты requirements-engineer + конвертер tasks→manifest
  (мелочь) + approval-шаг в IT Lead (переиспользование clarifications) +
  archive-шаг в docs (среднее). Итого ~2–3 рабочих дня, без новых рантаймов.

## Итоги пилота (26.11.2026)

Цикл пройден целиком: живые specs → change (proposal/дельта/design/tasks) →
человеческий approval → apply (task-1795676409000, product_id=7) → archive
(дельты влиты в `openspec/specs/favorites`, change в `archive/2026-11-26-add-favorites`).

**Наблюдения:**
- кодер на спеке ведёт себя лучше: реализовал фичу с нуля верно и **сам
  написал puppeteer-тесты по WHEN/THEN-сценариям**, отметил tasks.md [x] —
  сценарии спецификации превращаются в проверки без дополнительных указаний;
- approval в пилоте прошёл без правок (цена — ноль, польза — зафиксированное
  «до»-состояние; полная ценность раскроется на спорных фичах);
- пилот вскрыл **два реальных бага доставки** платформы, не связанных с
  OpenSpec: gitlink вместо дерева при пуше из rework-workspace и невозможность
  перетереть его повторным add (оба исправлены: .git в джанк-фильтре +
  git rm --cached перед копированием). Без «неудобного» спека-флоу они бы
  ещё долго ждали своей очереди;
- метрики: зелёнополяная перепись без спеки (прогон №1) — 2 часа отладки
  платформы и подменённый сайт; продуктовый прогон без спеки (№2) — 21 мин
  чисто; продуктовый со спекой (№3) — сборка ~10 мин, +2 рестарта из-за багов
  доставки (теперь починены навсегда).

**Решение: P2 принимаем** — requirements-engineer генерирует change-папку,
approval через колокольчик (текст change'а в вопросе), tasks.md → MANIFEST,
приёмка QA по сценариям. P3 (archive-автоматизация + браузер зеркала) —
по мере надобности.
